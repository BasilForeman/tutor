# PROJECT SPECIFICATION
## Tutor CRM — Telegram Bot & Analytics

**Версия:** 1.0  
**Назначение:** техническое и бизнес-описание проекта для AI-разработчика.

---

# 1. Описание продукта

Tutor CRM — внутренняя CRM-система для автоматизации работы по привлечению учеников и передаче их репетиторам.

Основной пользователь системы — Соня, которая самостоятельно находит учеников через различные каналы, связывается с ними, подбирает репетиторов и получает комиссию за передачу учеников.

Система должна автоматизировать:
- учёт репетиторов;
- учёт учеников;
- регистрацию источников привлечения;
- регистрацию заявок;
- передачу учеников репетиторам;
- учёт пробных и платных занятий;
- расчёт комиссий;
- учёт задолженностей;
- регистрацию платежей;
- возвраты и перерасчёты;
- автоматическую аналитику;
- синхронизацию с Google Sheets.

**Основной интерфейс:** Telegram Bot.

**Основное хранилище данных:** PostgreSQL.

**Аналитическая витрина:** Google Sheets.

# 2. Технологический стек

Использовать существующий стек проекта:
- Python;

- asyncpg;
- Google Sheets API;

Приложение должно сохранять асинхронную архитектуру.

Не внедрять новые библиотеки без необходимости. Если новая зависимость действительно нужна, обосновать её.

# 3. Архитектура

Сохранять существующее разделение ответственности:

- database — модели и подключение к БД;
- services — бизнес-логика;
- handlers — обработчики Telegram;
- keyboards — клавиатуры;
- states — FSM;
- integrations — внешние интеграции;
- main.py — точка входа.

Не переносить бизнес-логику в Telegram handlers.

PostgreSQL является единственным источником истины. Google Sheets используется как аналитическая витрина и не должен становиться основным хранилищем.

# 4. Основные бизнес-сущности

## 4.1. Tutor

Репетитор.

Хранить:
- ID;
- nickname;
- предмет;
- дату создания;
- статус активности;
- дополнительные параметры при необходимости.

## 4.2. Client

Ученик.

Хранить:
- ID;
- nickname;
- контакт;
- комментарий;
- статус активности;
- дату создания.

## 4.3. LeadSource

Источник привлечения.

Примеры:
- Telegram;
- Threads;
- Profi.ru;
- Avito;
- другие источники.

Хранить название и статус активности.

## 4.4. Lead

Заявка на поиск репетитора.

Хранить:
- Client;
- LeadSource;
- предмет;
- комментарий;
- статус;
- причину потери;
- дату создания.

Заявки не удалять при неудачном привлечении.

Предусмотреть историю изменения статусов.

## 4.5. Assignment

Факт передачи ученика конкретному репетитору.

Хранить:
- Lead;
- Tutor;
- Client;
- LeadSource;
- дату передачи;
- кто передал;
- стоимость занятия;
- индивидуальные условия комиссии;
- согласованную комиссию;
- срок оплаты;
- причину завершения;
- статус;
- комментарии.

Один ученик может иметь несколько передач разным репетиторам.

Повторная передача должна создавать новый Assignment. История предыдущей передачи сохраняется.

Комиссионные условия необходимо фиксировать на уровне конкретного Assignment, чтобы изменение стандартных настроек не влияло на старые передачи.

## 4.6. Lesson

Проведённое занятие.

Хранить:
- Assignment;
- дату;
- тип занятия;
- статус;
- стоимость;
- комментарий;
- дату создания.

Типы:
- trial — пробное;
- paid — платное.

Статусы:
- completed — проведено;
- cancelled — отменено.

Пробное занятие не создаёт комиссию.

Отменённое занятие не должно автоматически считаться проведённым.

## 4.7. Payment

Платёж репетитора.

Хранить:
- Assignment;
- дату платежа;
- сумму;
- комментарий;
- дату создания.

Поддерживать несколько частичных платежей для одного Assignment.

## 4.8. AssignmentFinance

Финансовое состояние передачи.

Необходимо учитывать:
- согласованную комиссию;
- начисленную комиссию;
- оплаченную комиссию;
- остаток задолженности;
- дату возникновения обязательства;
- установленный срок оплаты;
- фактическую дату погашения;
- количество дней просрочки.

Продумать, нужна ли отдельная сущность для начислений и корректировок. Не ограничиваться одним агрегированным финансовым полем, если это мешает аудиту истории.

## 4.9. Adjustments

Отдельный механизм возвратов и перерасчётов.

Хранить:
- Assignment;
- первоначальную сумму комиссии;
- скорректированную сумму;
- разницу;
- причину;
- дату;
- автора корректировки.

Не удалять предыдущие финансовые операции при перерасчётах.

# 5. Бизнес-логика комиссии

Финансовые условия индивидуальны и должны настраиваться при создании Assignment.

Предусмотреть следующие режимы:

1. Фиксированная сумма.
2. Комиссия в количестве почасовых ставок.
3. Процент от заработка репетитора.
4. Ручная сумма комиссии.
5. Индивидуальный сценарий с абонементом.

Базовый ориентир — 4 стоимости занятия.

Типичный диапазон — 2,5–4 стоимости занятия.

## 5.1. Пробное занятие

Первое пробное занятие бесплатное.

Комиссия за него не начисляется.

## 5.2. Обучение по отдельным занятиям

Если ученик занимается без предварительно оплаченного абонемента:

- система регистрирует каждое занятие;
- пробные занятия исключаются из расчёта;
- учитываются только проведённые платные занятия;
- задолженность по базовому сценарию начинает учитываться с четвёртого проведённого платного занятия;
- система фиксирует дату возникновения задолженности;
- после возникновения задолженности начинается контроль срока оплаты.

Для обучения, которое завершилось не более чем после четырёх занятий, обычно применяется комиссия 25% от стоимости занятия.

Эти правила являются стандартными договорённостями, а не жёстко зашитыми ограничениями.

## 5.3. Абонементы

Если репетитор и Соня договорились об оплате комиссии по абонементу:

- комиссия определяется заранее;
- её можно оплатить сразу;
- момент приобретения абонемента (после первого, третьего или другого занятия) не должен влиять на согласованную сумму;
- система должна сохранять дату приобретения абонемента и дату оплаты комиссии;
- нельзя повторно начислять уже оплаченную комиссию.

Если абонемент покрывает более четырёх занятий, необходимо отдельно учитывать согласованную комиссию и факт её оплаты.

## 5.4. Досрочное прекращение обучения

Обычно применяется комиссия в размере 25% от фактического заработка репетитора за проведённые занятия.

Однако условия индивидуальны.

Соня должна иметь возможность:
- изменить итоговую комиссию;
- указать причину;
- зафиксировать фактическую сумму;
- сохранить историю перерасчёта.

Нельзя автоматически применять одну формулу ко всем случаям.

# 6. Контроль задолженности и платежей

Для каждого Assignment необходимо определять:

- дату возникновения долга;
- установленный срок оплаты;
- фактическую дату оплаты;
- сумму долга;
- сумму частичных оплат;
- остаток;
- количество дней просрочки.

Ожидаемый срок оплаты по базовому сценарию — день проведения четвёртого платного занятия.

Показатели своевременности:

- оплата до четвёртого занятия — досрочная;
- оплата в день четвёртого занятия — своевременная;
- оплата на следующий день — своевременная;
- оплата позднее — просроченная.

Отдельно рассчитывать:
- среднюю задержку;
- долю своевременных оплат;
- количество неоплаченных задолженностей;
- общую просроченную сумму.

Для индивидуальных договорённостей срок оплаты должен настраиваться.

# 7. Аналитика

Аналитика является одной из главных целей проекта.

Необходимо предусмотреть следующие направления.

## 7.1. Репетиторы

- рейтинг репетиторов;
- количество переданных учеников;
- количество успешных передач;
- количество проведённых занятий;
- количество возвратов;
- сумма комиссий;
- сумма оплаченных комиссий;
- текущая задолженность;
- средняя задержка платежей;
- доля своевременных оплат.

Рейтинг должен учитывать надёжность и финансовую дисциплину, а не только количество полученных учеников.

Методологию рейтинга документировать. Не использовать произвольные веса без обоснования.

## 7.2. Источники привлечения

- количество заявок по источникам;
- количество успешных передач;
- конверсия из заявки в передачу;
- количество потерянных заявок;
- причины потери;
- динамика по источникам;
- средняя комиссия с успешной заявки;
- наиболее эффективные источники.

## 7.3. Временная аналитика

- количество заявок по дням недели;
- количество передач по дням недели;
- среднее количество заявок в сутки;
- динамика по неделям;
- динамика по месяцам;
- выявление наиболее эффективных дней.

## 7.4. Финансы

- общая согласованная комиссия;
- начисленная комиссия;
- оплаченная комиссия;
- текущая задолженность;
- просроченная задолженность;
- средняя комиссия на успешную передачу;
- средняя комиссия Сони с одной успешной заявки.

Среднюю комиссию с одной успешной заявки рассчитывать с учётом первоначальной комиссии, ограниченной первыми четырьмя занятиями, без дальнейших начислений при долгосрочном сотрудничестве.

Исключения и перерасчёты должны отражаться отдельно.

## 7.5. Возвраты и перерасчёты

- количество возвратов;
- причины возвратов;
- количество досрочных прекращений;
- суммы корректировок;
- первоначальная и итоговая комиссии;
- распределение причин прекращения обучения.

## 7.6. Платёжная дисциплина

- рейтинг своевременности оплаты;
- среднее время погашения;
- задержки по каждому репетитору;
- количество просрочек;
- сумма неоплаченных комиссий.

3. Добавить источник привлечения.
