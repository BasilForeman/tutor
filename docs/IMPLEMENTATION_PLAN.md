# Tutor CRM — план реализации

Приоритеты следуют `PROJECT_SPECIFICATION.md`. Существующие staged-изменения считаются пользовательской работой: перед правками сохранять их и изменять только необходимое. Миграции и запуск приложения делать только на отдельной тестовой БД. Секреты не копировать и не раскрывать.

## P0 — целостность данных и основные операции

**Готово в текущей ветке:** добавлены спецификация, план/аудит, SQL-миграции 0001–0005, безопасное поведение `create_tables.py` для непустых БД, FSM Assignment/Lesson/Payment, сервисы регистрации занятий и платежей, экран долга/переплат и 23 unit-теста. Миграции ещё не применены; другие режимы комиссии, refunds, остальная история/CRUD остаются в работе.

### P0.1 Схема, ограничения, миграции

- **Новые файлы:** `alembic.ini`, `migrations/env.py`, revision scripts или эквивалент, если выбранный migration tool уже присутствует после полной проверки зависимостей; `tests/conftest.py` и фабрики для изолированной БД.
- **Изменяемые:** `bot/database/models.py`, `bot/database/connection.py`, `requirements.txt`, `.gitignore`; возможно `create_tables.py` — заменить неявный production-путь на управляемую миграционную команду, сохранив совместимость данных.
- Зафиксировать фактическую текущую схему и тип `assignment_finances`; добавить FK/индексы/check constraints аддитивно. Нужна таблица истории статусов Lead, Lesson, запись начислений и журнал корректировок. Защитить существующие данные backfill-ом и проверкой конфликтов.
- Ввести `Numeric(precision, scale)` после проверки диапазона имеющихся данных; не обрезать суммы. Денежные входы принимать только через Decimal, отклонять отрицательные/не конечные суммы.
- **Зависит от:** доступа к коду и копии БД/схемы. Не применять на production.
- **Текущий статус:** SQL 0001–0005 подготовлены как ручные аддитивные migration scripts; 0001 создаёт historical Lead для каждой старой передачи и сохраняет прежнюю таблицу агрегата. Автоматического migration ledger пока нет, миграции не применялись.
- **Готово, когда:** миграции проверены на копии/fixture с существующими данными, порядок применения отмечен в migration ledger, FK и ограничения соответствуют данным, откат не удаляет данные молча.

### P0.2 Репетиторы, ученики, источники, заявки

- **Изменяемые:** существующие `bot/services/{tutors,clients,lead_sources,leads}.py`, `bot/handlers/{tutors,clients,lead_sources,leads}.py`, их keyboards/states.
- Завершить создание, список, поиск, детальную карточку, изменение и архивирование; фильтры по активности/статусу; история Lead status с причиной потери.
- Проверять все текстовые вводы, callback/message context и отсутствие дубликатов в БД конкурентно. Экранировать пользовательские значения в Telegram.
- Не физически удалять связанные сущности.
- **Готово, когда:** сценарии доступны в боте и сервисы проверены негативными входами и сохранением связей.

### P0.3 Assignment

- **Новые:** Assignment FSM/handler/keyboards, только если нет пригодного файла; тесты сервисов.
- **Изменяемые:** `bot/database/models.py`, `bot/services/assignments.py`, `bot/main.py`, клавиатура главного меню.
- Разрешить повторную передачу после прежнего Assignment, сохраняя каждый факт передачи; блокировать только конкурентный дубль одной операции. Сохранять snapshot комиссии/режима/срока и связь с Lead.
- Проверять что Lead, Tutor, Client и Source активны/существуют, как это допускает контракт; учитывать потерянные заявки и допустимые переходы.
- **Текущий статус:** FSM создания, списка и закрытия передачи подключён; сервис блокирует выбранный Lead, операция имеет уникальный idempotency key. Комиссия хранится как множитель ставки; обычное начисление наступает на четвёртом paid completed уроке. Закрытие в короткий срок создаёт корректировку 25% фактического заработка с причиной и автором. Unit-тесты покрывают расчёт и сохранение корректировки.
- **Готово, когда:** Telegram сценарий проверен на PostgreSQL; конкурентные запросы проверены БД.

### P0.4 Lessons и финансы/Payments

- **Текущий статус:** модель, сервис и Telegram FSM занятия реализованы для trial/paid и completed/cancelled; платный урок записывается с Decimal-доходом, на пороге оплаты устанавливается дата долга. Payment service/FSM обрабатывает частичные оплаты до начисленного остатка. Реализован финансовый view и Adjustment при закрытии short-term. Unit-тесты сервисов проходят.
- **Новые:** `bot/services/lessons.py`, `bot/handlers/lessons.py`, keyboards/states; `bot/services/finance.py` (реализован для короткого закрытия); `bot/services/payments.py`, handlers/states; модели `Lesson`, `AssignmentAdjustment`.
- **Изменяемые:** `models.py`, `assignments.py`, главная клавиатура, `main.py`.
- Проводить только completed paid lessons в расчёт согласно снимку договорённости. Trial/cancelled не создают начисление. Уникальный event key/constraint исключает повторное начисление одного занятия.
- Платежи как append-only события с частичными оплатами и идемпотентным operation key; остаток рассчитывается из ledger. Не принимать сумму выше долга без явного правила, выбранного Сониной договорённостью.
- Текущая реализация поддерживает индивидуальный множитель для долгосрочного режима и 25% от actual earnings при ручном закрытии после 1–4 уроков. Осталось: режимы fixed/percent/manual/subscription, произвольный adjustment, возврат переплаты и хранение начислений по каждому уроку. Порог закрытия сохраняется в Assignment и по умолчанию равен 4.
- Каждая связанная операция в транзакции; история не перезаписывается.
- **Готово, когда:** четвертое занятие, пробное, отмена, абонемент, частичная/полная оплата и повтор запроса сверяются с ledger на тестовой БД.
